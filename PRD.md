# PRD — ocrmd

> What ocrmd is for and whom it serves: the problem, users, goals and non-goals, current features, requirements, proposed success metrics and open questions.

Product requirements for [`bamr87/ocrmd`](https://github.com/bamr87/ocrmd), derived from the README, agent docs, config and code in this repo. Anything not stated in those sources is marked **TBD**; success metrics are proposals.

## 1. Overview / problem

ocrmd turns physical books and loose pages into cross-checked Markdown, plain text and JSON from a webcam, a folder of photos or a PDF, and keeps an inventory of everything scanned. Every page is read twice (local OCR engines and a vision model, Claude by default) and the readings are diffed, flagging disagreements rather than silently picking one.

## 1.1 Missions

ocrmd's direction is to become the ultimate open home for all things document digitization — data, tools, resources and transparency, gathered in one place that anyone can inspect and reuse.

1. **Provide data, tools, resources and transparency for all stakeholders, archivists, librarians, scholars and digitization practitioners, and the general public.** Anyone turning paper into text is a first-class audience. The aim is a shared, inspectable commons: the same readings, the same diffs, and the same inventory for everyone.
2. **Turn physical books and loose pages into cross-checked Markdown, plain text and JSON, and flag disagreements rather than silently picking a winner.** Every page is read twice — local OCR engines and a vision model, Claude by default — from a webcam, a folder of photos or a PDF, so provenance stays visible on the page.
3. **Keep a searchable inventory of everything scanned, work fully offline when the model pass is deferred, and send only page images off the machine, and only to the configured provider.** Accuracy, disagreement markers and local-first operation are the default path, not a later mode.

These missions set the course; they do not claim the work is finished. They serve the PRD goals: accurate transcriptions with visible disagreement, a searchable inventory, an offline OCR-only path, and a tight rule for what may leave the machine.

**Requirement**

- MR1: Constitution §1 states one direction statement and exactly three numbered missions, and the README and AGENTS.md taglines match that direction and link to constitution §1.

Feature [OCRMD-011](features/features.yml) traces to requirement MR1.

## 2. Target users

- People digitizing books and documents (e.g. study material) on a Mac
- The same people with a phone as the camera and a review screen (iOS and Android), paired with their own computer
- Developers embedding the pipeline via `ocrmd.api.Library`
- Downstream systems receiving pages via the destination HTTP contract (e.g. law-ai)

## 3. Goals and non-goals

**Goals**

- Accurate page transcriptions with visible disagreement markers
- A searchable SQLite inventory across all scanned pages
- Work offline (OCR-only) with the LLM pass deferrable
- Only page images leave the machine, and only to the configured provider

**Non-goals**

- Cloud hosting / multi-user service: TBD (not described)
- Silent auto-correction of disagreements

## 4. Core features (current)

- CLI: scan, ingest (incl. `--watch`), verify (incl. Batches API), review, status, reprocess, delete, build, read, library, search, export, send, etl, ocr-bench, doctor, serve (incl. `--lan`), pair, devices
- Local OCR: Apple Vision + RapidOCR voting (Tesseract fallback)
- Vision-model providers: Anthropic (default) and xAI
- Corpus per document (`documents/<slug>/pages/NNNN.md`) with rich front matter
- Exports: md, txt, json, jsonl; local web UI
- Phone app (iOS, Android): capture into an offline queue and review, against the operator's own server (`serve --lan`, `pair`, `devices`, `/api/v1`)
- Structured-data ETL pipelines and destinations

## 5. Requirements

**Functional**

- FR1: Each page stored as Markdown with front matter and both readings reconciled
- FR2: `ocrmd doctor` reports engines, cameras, credentials and DB health
- FR3: Config via `ocrmd.toml` / user config / `OCRMD_*` env / CLI flags (in increasing precedence)

**Non-functional**

- NFR1: Python ≥ 3.12; macOS primary (Linux/Windows via RapidOCR)
- NFR2: Test suite (~306 checks)
- NFR3: Cost awareness: `doctor --costs`, batch mode at reduced price

**Functional (planned — cycle 1 day 20 deep dive)**

- FR4: An optional on-machine vision-language model can be the second reading, so page images need not leave the machine; the default remains Claude, and disagreements stay visible in the Markdown (OCRMD-008)
- FR5: Born-digital PDFs can take a structure-aware path (layout, tables, reading order via Docling or Marker) that is still reconciled against the PDF text layer, the local engines and the vision pass (OCRMD-009)
- FR6: Ruled tables on camera scans are reconstructed as tables, not flattened prose, before reconcile (OCRMD-010)

**Functional and non-functional (phone app — ADR 0002)**

- FR7: A phone (iOS or Android) paired with the operator's own ocrmd can capture pages into an offline queue that uploads when the computer is reachable, report what each capture became, and review pages (resolve disagreements, edit, sign off); every page is still read and reconciled on the computer, never on the phone (OCRMD-012, OCRMD-013)
- NFR4: Another machine reaches the server only with a paired device's token, obtained once by exchanging a one-time, expiring code made on the computer; codes and tokens are stored only as hashes; loopback behaviour is unchanged; the phone's API (`/api/v1`) is versioned, typed and generated, and changes additively (OCRMD-013)

## 7. Roadmap / open questions

- Supported non-macOS camera capture: TBD (a phone is now an alternative to the webcam on any platform, FR7)
- Phone app: HTTPS for the LAN link, background upload, store distribution and on-device OCR as additional evidence are not decided (ADR 0002)
- xAI provider not exercised live (per README)
- Nougat was considered as a math/LaTeX specialist and is not proposed: it is narrow (arXiv-style English papers), slower, and appears unmaintained relative to Docling / olmOCR-class local VLMs
- Open PRs #22 and #26 both add a feature id OCRMD-007 (figure components vs constitution missions). This PR starts new ids at OCRMD-008 so either can keep 007. Rebase if those PRs land first and take 008+
